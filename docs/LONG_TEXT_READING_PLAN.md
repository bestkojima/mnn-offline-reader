# 下一阶段目标：英语长文连续朗读

状态：已确定目标，待实现。本文是下一阶段计划；现有 v0.2.0 Release 尚未实现此流水线。

## 用户目标

在其他 App 中选中或分享一大段英语文章，打开居中卡片，点击朗读：等待第一句合成后开始出声；播放当前句的同时合成后面的句子。在设备合成速度允许时，后续句子连续播放，没有等待合成造成的额外停顿，保留语言本身的自然停顿。

继续使用下载获得的 Supertonic 3 MNN int8、当前音色与语速选项，全程离线处理文字。英语为本阶段优先实现与验收的语言。

## 当前实现与改动原因

- `TextNormalizer.chunks()` 按空格和约 240 字符分块，不是英语语句切分。
- `SpeechController.run()` 在一个工作线程中依次合成、播放，并等待整块播放结束后才合成下一块。
- `play()` 为每块创建并释放 AudioTrack，没有贯穿全文的持续音频流。
- 卡片、控制器和分块器都限制最多 4,000 字符，需要共同调整。
- 当前支持停止与新请求替换，没有保留播放位置的真正暂停/继续。

## 交互范围

1. 保留 `PROCESS_TEXT`、分享文本和居中卡片；来源 App 仍须支持选字或分享。
2. 多句输入使用阅读模式，显示原文、当前句高亮与句子进度；保留单词查词和例句朗读。
3. 提供开始、暂停、继续和停止。暂停保留位置，停止清空本次阅读；停止后重新开始从文章开头朗读。
4. 检测整段语言，英语阅读会话固定为 `en`；识别不确定时允许手动选择。每个合成块独立添加一次 `<en>…</en>`，分句器处理原始文字。
5. 新文章或切换音色/语速终止旧会话并清空旧音频，用户重新开始后应用新设置，避免混用不同设置的预合成内容。
6. 长文上限初定 30,000 个 UTF-16 字符，入口、控制器和分句器共用限制；来源 App 与 Intent 传输限制仍然存在，不宣传无限长度。
7. 本阶段为卡片前台阅读：关闭卡片、返回来源 App 或进入后台即停止。后台/锁屏阅读与通知栏控制另设阶段，需要媒体播放前台服务及独立生命周期设计。

## 分句与合成分块

为每句保留原文起止位置，用于高亮和进度。展示句与合成块分开：很长的一句可以拆成多个合成块，但仍显示为同一句。

- 优先按 `. ! ?`、段落和其后的闭引号/括号识别句末，保留标点与原文顺序。
- 避免把 `Mr.`、`Dr.`、`e.g.`、`i.e.`、`U.S.`、姓名缩写、小数、网址和邮箱内部的点当成句末；缩写判断结合上下文，不仅匹配句号。
- 优先保留整句，超长句按分号、逗号、从句边界或空格再拆分。合成块初始沿用约 240 字符的保守上限，依据模型输入与设备表现调整。
- 第一完整句优先合成；首句过长时先合成其第一个自然语块，避免长首句拖慢启动。后续极短句是否合并由缓冲需求决定。
- 不切断英文单词、Unicode 代理对，不静默丢弃文字；无法合理处理的超长无空格内容明确提示。
- 一次建立原文位置映射，逐块调用已有规范化与 token 化，不逐句重新检测语言或加载模型。

## 合成与播放流水线

```mermaid
flowchart LR
    A[原文与句子位置] --> B[合成块列表]
    B --> C[单个合成工作线程]
    C --> D[有容量上限的 PCM 队列]
    D --> E[独立播放工作线程]
    E --> F[同一个 AudioTrack]
    F --> G[当前句高亮与进度]
```

单线程拥有并复用一个 MNN 引擎，按顺序合成。并行的是合成下一块与播放已完成的块，不并行执行多次推理。

第一块 PCM 就绪后尽快播放，不等待全文或固定两句全部生成。播放线程持续写入同一个 `MODE_STREAM` AudioTrack，合成线程提前准备后续块；仅在全文结束时等待剩余音频播完并释放播放器，不逐句排空和重建。

此方案采用 Android 的 [AudioTrack 流式接口](https://developer.android.com/reference/android/media/AudioTrack)。进度以实际播放的帧位置计算，不把“已写入设备缓冲”当成“用户已听完”；记录句子累计帧边界，并处理帧计数回绕及暂停。

## 缓冲与实时性

- 初始预合成目标为后续约 2 句，运行中按音频时长调节，目标缓冲约 5～20 秒。这些是待调参数，不是已测手机性能。
- 同时设置块数和字节上限，队列满时合成线程等待，播放释放空间后继续；不预先合成整篇并驻留内存。
- 队列、正在播放的 Java PCM 和短句缓存合计预算先沿用 10 MiB；长文 PCM 不重复存进短句 LRU。单次 JNI 合成临时数组、原生中间结果与系统音频缓冲另计，不能将此预算称为进程总内存上限。
- 复用模型、音色与资源校验结果。暂停时最多填满受限队列，之后停止生产，不无限预合成。
- 缓冲不足显示“正在缓冲”，等待后从原位置继续，不能跳句或假装完成；可适当提高后续缓冲目标，但不超过容量上限。

`RTF = 合成耗时 / 实际输出音频时长`，音频时长使用当前语速下的 PCM 样本数计算。首句等待包括模型加载、前处理和首块合成；冷、热启动分别记录。

例如下一块合成耗时 1 秒，当前块播放 4 秒，就有时间提前完成下一块。若长期平均 RTF 大于 1，有限缓冲终会耗尽，分句无法保证无限连续朗读。平均 RTF 小于 1 时，极短首句、偶发慢句、CPU 争用或热降频也可能造成不足。目标是消除当前串行调度引入的等待并吸收波动，不承诺所有设备绝对零卡顿。

## 暂停、取消与系统打断

会话状态包括 `PREPARING`、`PLAYING`、`PAUSED`、`BUFFERING`、`COMPLETED`、`STOPPED`、`ERROR`，提供一致的状态与当前句回调。

- 暂停 AudioTrack，保留未播 PCM、写入偏移与句子位置；继续沿用同一会话，不重读已听部分。
- 停止或新请求立即阻止出声，取消可取消的推理，唤醒队列等待者，丢弃旧输出并释放播放器。
- 保留请求代次标记，旧 JNI 结果、队列数据和 UI 回调不能影响新会话；不能并发销毁仍在推理的引擎。
- 错误、停止和末块完成均解除生产者/消费者等待；播放异常通知合成线程退出，避免死锁。
- 音频焦点打断、耳机拔出时暂停，等待用户继续，不自动抢回播放。遵循 [Android 音频焦点规则](https://developer.android.com/media/optimize/audio-focus)，持续阅读采用适合媒体播放的焦点请求。
- 后台释放与会话同步：先终止会话，再由合成所有者销毁模型。回到卡片后可以重新开始。

## 实施顺序

1. 新增英语分句/分块器及原文位置映射，统一长文限制。
2. 抽出合成块接口和会话数据，单线程继续拥有原生引擎。
3. 加入受限 PCM 队列、独立播放线程和共享 AudioTrack，接通提前合成。
4. 实现暂停/继续、实际播放进度和当前句高亮，处理替换、退出与音频打断。
5. 根据设备表现调整缓冲，发布说明明确长文能力和前台阅读边界。

主要入口为 `TextNormalizer.java`、`SpeechController.java`、`PronounceActivity.java`、`ReaderApplication.java`。分句和队列核心保持纯 Java、可独立验证；通过已有 ModelAssets/JNI 使用所选模型。

## 验收标准与待测项目

以下是后续实现的验收要求。本次仅记录目标，不运行构建、测试或性能测量。

| 项目 | 完成标准 |
| --- | --- |
| 长文 | 多段英语文章连续朗读，包含超过原 4,000 字符的输入，无漏句、重句和乱序 |
| 分句 | 缩写、小数、引号、段落、长句、无句末标点和 Unicode 保留原文顺序与位置 |
| 首句 | 首块就绪即开始，不等待全文或固定预生成多句；记录冷/热启动首次出声耗时 |
| 句间连续 | 下一块及时就绪时持续写入同一播放器；记录合成耗时、音频时长、队列深度、AudioTrack 欠载和缓冲事件，保留自然停顿 |
| 设备表现 | 指定并记录手机型号、音色，在 1.0×/1.25×和至少 5 分钟英语样本中确认是否持续无缓冲；关联实际 RTF、启动缓冲和热降频，不预先宣称达标 |
| 内存 | PCM 不随文章长度增长，队列满时停止生产；记录 Java PCM 与进程峰值内存 |
| 暂停/继续 | 暂停后不继续出声，继续不从头重来，不跳过设备内尚未播放的样本 |
| 停止/替换 | 队列满/空、推理中或播放中均可停止；旧文章不再出声或更新新状态，无死锁 |
| UI | 高亮跟随实际播放；完成、缓冲、暂停与缺模型提示准确 |
| 原有功能 | 短词、例句、下载恢复和中文入口仍可使用；中文流水线单独确认，不凭英语结果宣称达标 |

发布前设备验收及是否执行自动测试由后续工作安排决定。本次目标记录不触发 GitHub Actions，不更新现有 Release APK。
